## Overview
This repository contains the hardware-software co-design for accelerating the Mamba-3 State Space Model (SSM) on an AMD/Xilinx Kria 26 SOM. Following a software-hardware partition model, the host CPU manages data ingestion, control, and result checking, while the FPGA accelerator implements the selective state update itself, including the nonlinearities needed by that step. The design is written in C++ for Vitis HLS and supports both an fp32 baseline and a fixed-point exploration flow.

## System Architecture

The design is split into two primary components communicating over the Kria SOM's shared memory architecture:

1. **Host Application (`src/kria/host.cpp`):** Runs on the ARM processor. It prepares the sequential input tokens, loads the model weights/parameters, and sends the data to the hardware accelerator one at a time. It then retrieves the prediction results.
2. **Hardware Accelerator (`src/hls/mamba3_step.cpp`):** Synthesized onto the FPGA fabric. The DUT implements exactly one autoregressive Mamba step per invocation: it reads one step worth of tensors, performs the selective state update, evaluates the nonlinear terms (`exp`, `sigmoid`, `tanh`, and SiLU), and writes one `state_out` plus one `out`.

## How to Build and Run

### 1. Generate Golden Test Vectors

The C++ testbench compares against golden data produced by the PyTorch reference implementation. Run `generate_golden.py` to create the `data/` directory.

```bash
# 1. Generate golden data
python3 generate_golden.py          # creates data/ with *.bin files

# 2. Run C-simulation
make csim
```

### 3. Simulation and Synthesis (HLS)
To run C-simulation, C-synthesis, and generate the hardware module, use the top-level `Makefile`. This leverages the Tcl scripts located in the `artifacts/` directory.
```bash
# Run baseline fp32 C-Simulation to verify functional correctness
make csim

# Run baseline HLS synthesis to compile the C++ code into RTL
make dut
```

The csim testbench loads inputs and golden outputs from the `data/` directory and compares the DUT output against the PyTorch reference results (pass threshold: max absolute error < 0.5 on every step's output and the final state).

#### Build Configuration Knobs

The top-level `Makefile` exposes compile-time switches so you can choose between:

* the baseline fp32 design,
* the pragma-enabled optimization build,
* the fixed-point exploration build,
* the **CORDIC nonlinearity** build, and
* the **multi-step batching** build (TPOT optimization).

Useful helper commands:

```bash
# Print the current build configuration
make show-config

# Print a summary of common targets and overrides
make help
```

#### Baseline Build

```bash
# Baseline fp32 C-simulation
make csim

# Baseline HLS synthesis
make dut

# Baseline bitstream generation
make bitstream
```

#### Pragma-Enabled Optimization Build

Enable the optional HLS pragma path implemented directly inside `mamba3_step.cpp`:

```bash
# C-simulation with optimization pragmas enabled
make csim MAMBA3_ENABLE_HLS_PRAGMAS=1

# HLS synthesis with optimization pragmas enabled
make dut MAMBA3_ENABLE_HLS_PRAGMAS=1

# Bitstream generation with optimization pragmas enabled
make bitstream MAMBA3_ENABLE_HLS_PRAGMAS=1
```

#### Fixed-Point Exploration Build

Enable fixed-point internal arithmetic while keeping the stream interface in fp32:

```bash
# Fixed-point C-simulation (piecewise-linear nonlinearities enabled automatically)
make csim MAMBA3_USE_FIXED_POINT=1

# Fixed-point HLS synthesis with pragmas enabled
make dut MAMBA3_USE_FIXED_POINT=1 MAMBA3_ENABLE_HLS_PRAGMAS=1

# Fixed-point bitstream generation with pragmas enabled
make bitstream MAMBA3_USE_FIXED_POINT=1 MAMBA3_ENABLE_HLS_PRAGMAS=1
```

The default fixed-point format is `ap_fixed<24,10>`. You can override it from `make`:

```bash
make csim MAMBA3_USE_FIXED_POINT=1 MAMBA3_FIXED_TOTAL_BITS=24 MAMBA3_FIXED_INT_BITS=8
```

#### CORDIC Nonlinearity Build

Enable hyperbolic CORDIC-based `exp`, `sigmoid`, `tanh`, and SiLU:

```bash
# CORDIC C-simulation (fp32 types, CORDIC algorithm)
make csim MAMBA3_USE_CORDIC=1

# CORDIC + fixed-point
make csim MAMBA3_USE_CORDIC=1 MAMBA3_USE_FIXED_POINT=1

# CORDIC synthesis with pragmas
make dut MAMBA3_USE_CORDIC=1 MAMBA3_ENABLE_HLS_PRAGMAS=1
```

When `MAMBA3_USE_CORDIC=1`, the nonlinear functions use a 24-iteration hyperbolic CORDIC kernel (shifts 1–22 with the standard repeats at 4 and 13). This provides an alternative to piecewise-linear (PWL) tables and is especially useful for fixed-point synthesis where `hls::exp`/`hls::tanh` are unavailable or expensive.

#### Multi-Step Batching Build

Amortize constant tensor streaming by processing multiple autoregressive steps per DUT invocation:

```bash
# Regenerate golden data with 4 autoregressive steps per sequence
python3 generate_golden.py --nsteps=4

# C-simulation with 4 steps per invocation
make csim MAMBA3_NSTEPS=4

# Synthesis with 4 steps
make dut MAMBA3_NSTEPS=4 MAMBA3_ENABLE_HLS_PRAGMAS=1

# Combined: CORDIC + multi-step + pragmas
make dut MAMBA3_USE_CORDIC=1 MAMBA3_NSTEPS=4 MAMBA3_ENABLE_HLS_PRAGMAS=1
```

When `NSTEPS > 1`, the DUT loads weight/projection tensors (A, D, xproj, outproj, zproj) once and loops over `NSTEPS` steps reading only the per-step varying inputs. State evolves in-place. This significantly reduces per-token AXI stream overhead and eliminates host↔FPGA round-trips between tokens.

Additional useful overrides:

```bash
# Control the pipeline initiation interval used by the optional pragma path
make dut MAMBA3_ENABLE_HLS_PRAGMAS=1 MAMBA3_PIPELINE_II=1

# Toggle MIMO-loop unrolling inside the DUT
make dut MAMBA3_ENABLE_HLS_PRAGMAS=1 MAMBA3_UNROLL_MIMO=1
```

### 4. Generating the Bitstream
Once HLS synthesis is complete and verified, generate the FPGA bitstream:
```bash
make bitstream
```

### 5. Deploying to the Kria Board

After successful bitstream generation and compiling the host program, deploy the application to the board using the provided shell script:
```bash
./deploy_on_kria.sh <board-ip-or-hostname>
```

## Appendix: Nonlinearity Notes

This appendix gives a short, practical explanation of the nonlinear functions used in the selective Mamba step and how they are implemented in this repository.

### 1. Where the nonlinearities appear in the kernel

The current step kernel uses the following nonlinear terms:

* `alpha = exp(A * dt)`
* `beta = (1 - trap) * dt * alpha`
* `gamma = trap * dt`
* `gate = z_val * sigmoid(z_val)` which is the **SiLU** activation

These terms are evaluated inside `src/hls/ssm_ops.h` and are used by the accelerator in both fp32 mode and fixed-point mode.

### 2. What each function means

#### Exponential: `exp(x)`

The exponential function grows quickly for positive `x` and shrinks quickly for negative `x`.

In this design it is mainly used for:

* `alpha = exp(A * dt)`

Since `A` is negative and `dt` is positive in this selective state update, the argument `A * dt` is typically non-positive. That matters because it means the implementation only needs to approximate the negative-side range accurately for this kernel.

#### Sigmoid: `sigmoid(x)`

The sigmoid function maps any real value into the range `(0, 1)`:

* `sigmoid(x) = 1 / (1 + exp(-x))`

It is used as a smooth gate. Large positive values move it close to `1`, large negative values move it close to `0`, and values near `0` land near `0.5`.

#### Hyperbolic Tangent: `tanh(x)`

The `tanh` function maps real values into `(-1, 1)`.

It is not used directly in the original Mamba math here, but it is very useful in the fixed-point implementation because sigmoid can be rewritten as:

* `sigmoid(x) = 0.5 * (1 + tanh(x / 2))`

That lets the design reuse a `tanh` approximation to compute sigmoid without needing a separate expensive floating-point exponential in fixed-point mode.

#### SiLU: `x * sigmoid(x)`

SiLU stands for **Sigmoid Linear Unit**. It is also called the swish activation.

In this project it appears as:

* `gate = z_val * sigmoid(z_val)`

Then the intermediate output is multiplied by this gate. This makes the output path data-dependent in a smooth way instead of using a hard threshold.

### 3. fp32 mode vs fixed-point mode

The repository supports two main math paths:

* **fp32 mode**: uses the normal `float` datapath. In this mode the helper functions call `hls::exp` / `hls::tanh` during synthesis and `std::exp` / `std::tanh` in software simulation.
* **fixed-point mode**: changes the internal compute type to `ap_fixed<...>` and replaces the transcendental nonlinearities with piecewise-linear approximations that are easier for HLS to synthesize.

The stream interface to the DUT remains fp32 in both modes. Only the internal arithmetic changes.

### 4. What “piecewise-linear approximation” means here

For fixed-point exploration, the nonlinear functions are not evaluated with a full floating-point transcendental implementation. Instead:

* the valid input range is clipped to a practical interval,
* a small lookup table stores sampled values of the function,
* the code finds the two neighboring table entries, and
* it linearly interpolates between them.

So instead of computing the exact curve everywhere, the curve is approximated by many short straight-line segments. This is much friendlier to FPGA hardware because it mostly uses:

* comparisons,
* additions,
* multiplications, and
* small ROM-style tables

### 5. How each approximation is implemented in this repo

#### Fixed-point `exp`

The fixed-point exponential path is tailored to the `A * dt` term in this kernel.

It works as follows:

* clip the input to a negative interval used by this design,
* perform range reduction using `x = k * ln(2) + r`,
* approximate `exp(r)` over a small reduced interval, and
* scale the result by a power of two to recover `exp(x)`

This is why the `exp` approximation can stay accurate without storing a huge table over a wide domain.

#### Fixed-point `tanh`

The fixed-point `tanh` path uses:

* symmetry: `tanh(-x) = -tanh(x)`
* clipping to a practical positive interval
* a lookup table plus linear interpolation

Because `tanh` saturates near `-1` and `1`, clipping is usually acceptable once the input magnitude is large enough.

#### Fixed-point `sigmoid`

There is no separate standalone sigmoid lookup table in the current implementation. Instead the code uses:

* `sigmoid(x) = 0.5 * (1 + tanh(x / 2))`

So the `sigmoid` approximation is built directly from the `tanh` approximation.

#### Fixed-point SiLU

Once sigmoid is approximated, SiLU is computed as:

* `silu(x) = x * sigmoid(x)`

So SiLU does not need its own lookup table either.

### 6. Where to look in the code

If you want to trace the implementation:

* `src/hls/typedefs.h` controls whether the internal datatype is `float` or `ap_fixed`
* `src/hls/ssm_ops.h` contains the helper functions for `exp`, `sigmoid`, `tanh`, and SiLU
* `src/hls/ssm_pwl_tables.h` stores the lookup tables used by the fixed-point approximation path
* `src/hls/mamba3_step.cpp` shows where those helper functions are applied inside the single-step DUT

### 7. Why this matters for design exploration

The main reason for this approximation strategy is that exact transcendental math is expensive and awkward in fixed-point HLS flows, while lookup-table plus interpolation logic is much easier to synthesize and tune.

This gives you a useful exploration space:

* wider or narrower fixed-point formats
* more or fewer lookup-table segments
* exact fp32 math vs approximate fixed-point math
* different pragma settings for throughput/area tradeoffs

### 8. Important limitation

The current approximation ranges are tuned for the selective Mamba step implemented in this repository and for the observed value ranges of the shipped sample data. If the model configuration or data distribution changes significantly, the approximation tables or clipping ranges may need to be retuned.
